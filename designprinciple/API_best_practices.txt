"How do you define a new REST API? What are the important things you consider while designing an API?"


1. Understand Business Requirements:
The first step is understanding what business capability the API should provide.

Suppose we are designing an Order Management System.

Functional Questions
Who can create orders?
Can guest users order?
Can users modify orders?
Can users cancel orders?
Can an order contain multiple products?
Can an order be partially cancelled?

Non-Functional Questions
Expected requests per second?
Response time SLA?
Internal or external API?
Security requirements?
Data consistency requirements?
Audit requirements?


2. Identify Resources:
REST APIs are based on resources, not actions. URLs represent nouns not actions.

Bad

POST /createOrder
GET /fetchOrder
POST /cancelOrder

Good

POST /orders
GET /orders/{orderId}
PATCH /orders/{orderId}
DELETE /orders/{orderId}



3. API Naming Convention: Use meaningful resource names.

Bad

/GetEmployee

Bad

/Employee

Good

/employees

Nested resources /customers/{id}/orders
Instead of       /orders?customerId=123

Rules

lowercase
plural nouns
no verbs
hyphen instead of underscore

Good

/customer-orders


4. Choose Correct HTTP Method: This is one of the favorite interview questions.

5. API Versioning:
Eventually APIs change. Existing clients should never break.

URI Versioning
/v1/orders
/v2/orders

Header Versioning
Accept:
application/vnd.company.v2+json   (Used by some organizations.)

Query Version
/orders?version=2    Avoid.

6. Request DTO Design: Never expose database entities.

                       Bad

                       {
                       "id":100,
                       "createdAt":"...",
                       "isDeleted":false,
                       "isInternal":true,
                       "version":10
                       }

                       These are internal fields.

                       Good

                       {
                       "customerId":"123",
                       "items":[
                       {
                       "productId":"P100",
                       "quantity":2
                       }
                       ]
                       }

11. Idempotency:

Very important for payment APIs.



Without idempotency

Charge ?1000

Charge ?1000

Charge ?1000

Triple payment.

Solution

POST /payments

Header

X-Idempotency-Key:
123ABC

Server stores

123ABC

Payment Success

Retry with same key returns previous response.

No duplicate payment.


12. Pagination:

Never

GET /employees

Suppose

10 million rows.

Server crashes.

Use

GET /employees?page=1&size=20

Better

Cursor pagination

GET /employees?cursor=xyz123

Cursor pagination is preferred for large datasets because it avoids expensive OFFSET scans
and provides stable results when new records are inserted.

23. API Documentation:

Use OpenAPI/Swagger.

24. Backward Compatibility:

Never remove existing fields.

Old

{
"name":"Amit"
}

Need new field

{
"name":"Amit",
"fullName":"Amit Singh Tomar"
}

Deprecate old field gradually instead of breaking clients.






25. API Design Principles
Consistency: Use the same naming and response format across all APIs.
Statelessness: Do not store client session state on the server.
Idempotency: Critical for retryable operations.
Loose Coupling: Clients should not depend on internal implementation.
Resource-Oriented Design: Model business entities, not actions.
Extensibility: Design APIs so new fields can be added without breaking clients.
Security by Default: Authentication, authorization, encryption, input validation.
Observability: Logs, metrics, tracing, audit trails.
Performance: Pagination, compression, caching, efficient payloads.
