
How to Eliminate / Reduce Multiple Joins (>= 3) in SQL >>>

First principle: You don’t eliminate joins blindly — you eliminate unnecessary data movement.

Joins are expensive when:
Tables are large.
Join keys are not selective.
Data is distributed (sharded / cross-node).
Query is in a hot path.
So the goal is query efficiency, not “zero joins”.

1. Denormalization (Primary Strategy): Denormalization is intentionally duplicating data to eliminate expensive joins
in read-heavy systems, trading write complexity and consistency guarantees for predictable low-latency reads.
In simple words: You copy data so you don’t have to JOIN.
How to achieve Denormalization/Common Denormalization Patterns:

-Attribute Duplication (Most Common):
 Normalized:
 orders(order_id, customer_id)
 customers(customer_id, name, city)

 Query:
 SELECT o.order_id, c.name, c.city
 FROM orders o
 JOIN customers c ON o.customer_id = c.customer_id;

 Denormalized:
 orders(order_id, customer_id, customer_name, customer_city)

 Now:
 SELECT order_id, customer_name, customer_city FROM orders;

 Join eliminated completely.

 -Precomputed Aggregates:
Instead of computing aggregates repeatedly:

SELECT customer_id, COUNT(*)
FROM orders
GROUP BY customer_id;

Store:
customers (
  customer_id,
  total_orders
)

Update on write: UPDATE customers SET total_orders = total_orders + 1;
Used heavily in: Dashboards, Metrics, Leaderboards.

-Embedded Data (Document-style Denormalization):
Common in NoSQL but also valid in SQL (JSON columns).

Example:
order {
  order_id,
  customer: {
    name,
    phone,
    city
  },
  items: [...]
}
Read in one fetch, zero joins.

-Flattened Read Tables (CQRS Pattern):
Write model (normalized): orders, users, payments
Read model (denormalized):

order_read_model (
  order_id,
  user_name,
  payment_status,
  delivery_city
)

Updated via: Events, CDC (Change Data Capture), Background jobs.

2. Replace Joins with Precomputed Tables / Materialized Views:

3. Convert Joins into Subqueries (When Selectivity Is High):
Sometimes this is faster:

SELECT *
FROM orders o
WHERE o.customer_id IN (
  SELECT c.id
  FROM customers c
  WHERE c.country = 'IN'
);

Instead of: JOIN customers c ON o.customer_id = c.id

4. Use Semi-Joins / EXISTS Instead of Full Joins:

Instead of: JOIN payments p ON o.id = p.order_id
    Use:    WHERE EXISTS (
              SELECT 1 FROM payments p
              WHERE p.order_id = o.id
            )
Benefits: Stops scanning after first match, Less data movement, No row multiplication.

5. Push Filters Before Joins (Join Reduction):
    Bad:
                FROM orders o
                JOIN customers c ON o.customer_id = c.id
                WHERE c.country = 'IN'
    Good:
                FROM orders o
                JOIN (
                  SELECT id FROM customers WHERE country = 'IN'
                ) c ON o.customer_id = c.id
This reduces: Join input size, Memory usage, Shuffle cost (in distributed DBs).

6. Use Covering Indexes to Avoid Join Lookups: Sometimes you don’t need to eliminate the join — just avoid table access.

Example:
        CREATE INDEX idx_customer_country
        ON customers (id, country);
“Many join performance issues are actually indexing problems.”

7. Replace Joins with Application-Level Joins (Carefully):
In some systems:
Query primary table.
Fetch related data via batch calls.
Cache results.

Trade-off: More application logic, Risk of N+1 queries (call this out!)

8. Caching as a Join Elimination Strategy:
Cache dimension tables (users, products)
Cache final query result
Use Redis / Memcached

---------------------------------------------------
When NOT to Eliminate Joins (Important)
Say this to sound senior:
“If joins are selective, indexed, and local, removing them may worsen correctness and maintainability.”
